00

차별화 — 왜 "또 습관앱"이 아닌가

우리 프로젝트의 기준점. 이 한 줄이 발표 차별화와 기술 핵심을 동시에 규정한다.

시스템이 매일 개인화 배정하고, 완료가 성향을 키워 다음 퀘스트가 갈라진다.

배정 엔진과 성향 분기가 이 앱의 "뇌"이자, 이 프로젝트의 기술 하이라이트이자 발표 차별화 포인트다.

기존 습관앱 (Habitica 류)

유저가 스스로 목표를 세팅하고 반복 체크. 화면은 달라도 캐릭터는 모두 같다.

Life Quest

성향 벡터를 읽어 제약·가중 샘플링으로 배정. 유저마다 캐릭터가 갈라진다 — "같은 앱인데 내 플레이가 다르다."

01

아키텍처 — 3 코어 엔진 + 매칭

기능 나열(15개)을 버리지 않는다. 3개 시스템으로 흡수하면 "위시리스트"가 "설계된 시스템"이 된다. 핵심은 완료 이벤트가 도는 루프이고, 협동 퀘스트를 묶는 System D 매칭 엔진이 그 루프에 인접한다.

02

System A — 퀘스트 배정 엔진

앱의 뇌. "이 유저가 왜 이 퀘스트를 받았는가"를 설명할 수 있는 알고리즘 = 이 프로젝트의 기술 하이라이트.

A

일일 배정 엔진

CONSTRAINT-BASED WEIGHTED SAMPLING

● 기술 하이라이트

매일 자정 배치(또는 첫 로그인 트리거)로 유저별 N개를 배정한다. 하드 제약으로 후보를 거르고, 소프트 가중으로 성향·다양성·난이도를 반영한 뒤 가중 샘플링한다.

  • 하드 제약 — 최근 K일 중복 제외 · 레벨 게이팅(전설은 Lv 조건) · 위치 반경(선택)
  • 소프트 가중 — 성향 점수 · 카테고리 다양성(편중 방지) · 난이도 믹스(쉬운 것 + 도전 하나)
  • Exploration vs Exploitation — 성향 편식만 주면 도감이 안 채워진다. ε 확률로 안 해본 카테고리를 섞어 도감 완성 동기와 개인화를 동시에. 멀티암드밴딧의 향기를 ε-greedy로 단순 구현.
function assignDaily(user, N):
  pool = quests
    .filter(q → q.level_req <= user.level)          # 하드: 레벨 게이팅
    .filter(q → q.id not in recentHistory(user, K))  # 하드: 최근 K일 중복 제외
    .filter(q → withinRadius(q.place, user.loc))      # 하드: 위치(선택)

  for q in pool:
    q.weight = base
      * dispositionWeight(user.disposition, q.tags)   # 소프트: 성향 가중
      * diversityPenalty(picked.categories, q.category)# 소프트: 편중 방지
      * difficultyFit(user.level, q.tier)             # 소프트: 난이도 믹스

  selected = []
  repeat N times:
    if random() < EPSILON:                # exploration → 도감 유도
      pick = uniformFrom(unseenCategories(pool))
    else:                                # exploitation → 성향 최적
      pick = weightedSample(pool)
    selected.add(pick); pool.remove(pick)  # 비복원 추출

  return selected

설계 논점: 배치 vs 실시간 트레이드오프 · ε 값 튜닝 · 성향 편식과 다양성의 균형.

흡수한 기능 → 오늘의 퀘스트퀘스트 등급NPC 의뢰랜덤 이벤트 (Lucky Day)

04

System C — 파생 상태 엔진

완료는 이벤트다. 이벤트 하나가 여러 파생 집계를 갱신하는 도메인 이벤트 패턴 — 데이터 정합성의 핵심.

C

파생 상태 & 정합성

EVENT-DRIVEN AGGREGATION

● 정합성

완료 이벤트가 발행되면 핸들러들이 각자 파생 상태를 갱신한다. 하드코딩이 아니라 이벤트 구독 구조.

  • 파생 집계 — 업적 진행도(카페 10/30/100 = I~V 단계) · 도감 등록 · 수집률(%) · 콤보 스트릭(연속일)
  • 비밀 업적 = 조건 룰 테이블 — "비 오는 날 + 산 정상 = Storm Walker". 하드코딩 아닌 등록형 룰로 확장 가능하게.
  • 정합성 앵글 — 완료 트랜잭션의 멱등 처리(같은 완료 두 번 눌러도 EXP·집계 중복 금지, idempotency key) · 주간 랭킹 리셋 배치의 스냅샷 일관성.

멱등 처리가 없으면 중복 완료·연타에 EXP·업적이 오염된다 — 배포 품질의 최소 기준선.

흡수한 기능 → 업적 진화 I~VLifeDex 수집률컬렉션 배지콤보레벨업 보상
05

System D — 동행 매칭 엔진

협동 퀘스트를 함께할 사람을 묶는다. 스케일을 키우지 않는 게 원칙 — 먼저 가벼운 로비로 붙이고, 자동 매칭은 그 위에 얹는 심화 층.

D

동행 매칭 엔진

QUEUE-BASED MATCHMAKING

● 기술 하이라이트

2층 구조로 스코프 통제. ① 로비(경량 기본) — 방 생성 → 근처 사람 요청/수락 → 방 형성. ② 매칭 엔진(심화) — 대기열에 넣으면 성향·위치·시간으로 자동 페어링. 로비만으로도 동행 기능은 배포되고, 엔진은 그 뒤에 얹는다.

  • 스코어링 — 하드 필터(인증·평점·상호차단·같은 퀘스트·지역버킷) 후 성향 유사도 + 위치 근접 + 시간 겹침 − 레벨격차. 성향 벡터는 System B 재사용.
  • 큐 매치메이킹 — 대기 풀 + 주기적 매처. 수락 문턱 τ가 대기시간에 따라 완화 = 기아(starvation) 방지.
  • 동시성 — 두 유저를 원자적으로 함께 WAITING→PROPOSED로 CAS. 자원을 락으로 점유하는 게 아니라 큐 기반 낙관적 매칭 + 실패 시 재큐.
  • 안전 훅(경량) — 공공장소 POI에서만 만남 · 만나기 전 인앱 채팅 · 사후 평가/신고. 본격 신뢰·안전은 별도 트랙.
# 매처: 지역·퀘스트 버킷마다 T초 주기
for a in pool sorted by waitTime desc:      # 오래 기다린 유저 우선 = 기아 방지
    tau = base - relax(a.waitTime)          # 대기 길수록 문턱↓ = 반경 확장
    b   = argmax(score(a, c) for c in pool)
    if score(a, b) >= tau and claim(a, b):  # 원자적 동시 클레임
        propose(a, b)                       # 2단계 확정

# claim: 둘 다 WAITING일 때만 함께 PROPOSED (compare-and-set)
UPDATE match_pool SET status='PROPOSED'
WHERE user_id IN (a, b) AND status='WAITING'   # affected==2 이면 성공

2단계 확정 사가 — propose → 양쪽 수락(TTL 60s) → coop_room 생성. 한쪽 거절/타임아웃이면 보상: 수락자 풀 복귀 + (a,b) 재매칭 쿨다운. 멱등키로 부분 실패 복구.

설계 논점: 큐 매치메이킹(문턱 완화·기아) · 낙관적 매칭 + 확정 사가·보상·멱등 · geohash 공간 인덱스 · N>2 그룹 = 클러스터링(로드맵).

흡수한 기능 → 협동 퀘스트길드(파티)친구와 함께소셜 동행

스코프 & 역할 도메인

MVP는 핵심 8기능으로 고정. 역할은 도메인으로 나눠두고 배정은 팀 미팅에서 — 4개 도메인이 백엔드·프론트·앱으로 균형 잡힌다.

✅ MVP (4주 배포 타겟)

  • 회원가입 / 로그인 (JWT)
  • 퀘스트 배정 엔진 (A)
  • 완료 · EXP · 레벨
  • 도감 / 업적 파생 (C)
  • 친구 주간 랭킹
  • 마이페이지 · 성향 화면 (B)
  • 동행 로비 (경량 · D 엔진은 심화)

👥 역할 도메인 (미팅에서 배정)

  • 1 백엔드 — 배정·성향 엔진 (A·B)
  • 2 백엔드 — 파생상태·랭킹·정합성 (C) · 동행 매칭 (D)
