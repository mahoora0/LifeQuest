## 3. GPS 위치 인증 규칙 (담당: 팀원 2)

### 3-1. 인증 반경 기준 `[예시]`

| 장소 유형 | 반경 |
|---|---|
| 카페·음식점 | 50m |
| 공원·관광지 | 100m |
| 산·해변 등 넓은 장소 | 200~500m |

### 3-2. 처리 절차

1. 사용자가 위치 인증을 요청하면 현재 위도·경도를 전송한다.
2. 서버가 퀘스트 장소 좌표와의 거리를 계산한다(Haversine 공식).
3. 거리가 `radius_m` 이내면 인증 성공, 완료 처리로 이어진다.
4. 반경 밖이면 현재 거리와 필요한 이동 거리를 안내한다.

### 3-3. 오차·예외 처리

- 기기 GPS는 실내·건물 밀집 지역에서 수십~수백 m 오차가 발생할 수 있다. 클라이언트가 전달하는 `accuracy` 값을 참고해, 오차가 큰 경우 재시도를 안내한다 `[제안]`.
- 위치 권한이 꺼져 있으면 권한 요청 화면을 표시한다.
- 짧은 시간 내 비정상적으로 먼 거리를 이동한 것으로 감지되면(예: 도보로 불가능한 이동) 즉시 차단하지 않고 재확인을 요청한다 `[제안]` — 완전 차단은 정상 사용자의 오탐을 유발할 수 있어 지양한다.

### 3-4. 구현 유의사항

- 브라우저 Geolocation API는 보안 컨텍스트(HTTPS 또는 localhost)에서만 동작한다. 웹으로 배포하는 경우 HTTPS 구성이 필수 조건이다.
- 앱(Flutter)으로 빌드하는 경우 별도의 위치 권한 요청·백그라운드 위치 정책을 고려해야 한다.
- 발표·시연 환경에서는 실제 현장 이동이 어려우므로, 개발/테스트 빌드에 한해 위치 값을 임의로 지정할 수 있는 테스트용 입력을 마련해 둔다 `[제안]`(운영 빌드에는 포함하지 않음).

## 4. 퀘스트 완료 규칙 — 멱등성 (담당: 팀원 2)

- 완료 요청은 배정 기록(`USER_DAILY_QUESTS`) 단위로 1건만 유효하며, `QUEST_COMPLETIONS.user_daily_quest_id`의 UNIQUE 제약으로 보장한다.
- 중복 완료 요청 시: 오류를 반환하지 않고 **기존 완료 결과를 그대로 반환**한다(EXP 재지급 없음) `[제안]`.
- 직접 완료(SELF_REPORT) 퀘스트는 위치 검증 없이 사용자의 완료 버튼 입력만으로 처리한다. 사진 인증은 저장소 의존성이 추가되므로 MVP 범위에서 제외하고 Phase 2 후보로 둔다 `[제안]`.

## 5. EXP·레벨 규칙 (담당: 팀원 1)

### 5-1. 레벨 계산

다음 레벨까지 필요 EXP 공식 `[예시]`:

```
requiredExp(n) = 100 × n   (n → n+1 레벨로 가기 위해 필요한 EXP)
```

| 레벨 | 누적 필요 EXP | 구간 필요 EXP |
|---|---|---|
| 1 | 0 | - |
| 2 | 100 | 100 |
| 3 | 300 | 200 |
| 4 | 600 | 300 |
| 5 | 1,000 | 400 |
| 6 | 1,500 | 500 |
| 7 | 2,100 | 600 |
| 8 | 2,800 | 700 |
| 9 | 3,600 | 800 |
| 10 | 4,500 | 900 |

레벨 구간 명칭 예시: Lv.1 초보 모험가 · Lv.5 탐험가 · Lv.15 여행자 · Lv.30 마스터

### 5-2. 처리 순서

1. 퀘스트 완료 이벤트 수신(questId, grade, exp_reward)
2. `EXP_LOGS`에 지급 이력 기록
3. `USERS.total_exp` 누적
4. 누적 EXP 기준으로 레벨업 여부 판정
5. 레벨업 시 `LEVEL_REWARDS` 조회 후 보상 지급(칭호·프로필 아이템 등)

## 6. LifeDex 규칙 (담당: 팀원 3)

- 퀘스트에 `lifedex_item_id`가 연결된 경우, 완료 시 해당 항목을 `USER_LIFEDEX`에 자동 등록한다.
- 중복 등록은 `UNIQUE(user_id, lifedex_item_id)`로 방지한다(이미 보유한 항목은 재등록되지 않음).
- 진행률 = 카테고리별 (보유 항목 수 / 전체 항목 수)

## 7. 업적 규칙 (담당: 팀원 3)

- 조건 유형
  - `CUMULATIVE_COUNT`: 누적 횟수형(예: 카페 10곳 방문)
  - `SPECIFIC_QUEST`: 특정 퀘스트 완료형
  - `LIFEDEX_COUNT`: 도감 보유 수 연동형
- 단계별 업적은 `ACHIEVEMENT_STEPS`의 `required_count`를 순차 충족하며 `current_step`이 상승한다(예: 카페 탐험가 I → V).
- 비밀 업적(`is_secret = true`)은 목록 조회 시 미달성 상태에서 이름·조건을 마스킹 처리하고, 달성 시점에만 공개한다.

## 8. 칭호·보상 규칙 (담당: 팀원 1)

- 칭호 획득 경로: 레벨업 보상, 업적 단계 보상
- 사용자는 보유 칭호 중 하나만 대표 칭호로 설정할 수 있다.
- 대표 칭호는 해제(설정 안 함) 상태로 되돌릴 수 있다.

## 9. 친구 규칙 (담당: 팀원 4)

- 친구 요청 흐름: 요청 전송(`PENDING`) → 수신자 수락(`ACCEPTED`) 또는 거절(`REJECTED`)
- 동일 대상에게 대기 중인 요청이 있으면 중복 요청을 허용하지 않는다.
- 자기 자신에게는 요청할 수 없다.
- 수락 시 `FRIENDSHIPS`에 양방향 레코드를 생성한다.
- 친구 삭제 시 양방향 레코드를 모두 제거한다.

## 10. 랭킹 규칙 (담당: 팀원 4)

- 산정 기준: 누적 EXP(`total_exp`) 기준 `[예시]`(대안: 레벨 기준, 팀 확정 필요)
- `[TBD]` 실시간 구현 방식 — **제안 기본값**: MVP는 `USERS` 테이블 직접 쿼리(`ORDER BY total_exp DESC`)로 시작하고, 성능 이슈가 발생하면 Redis Sorted Set으로 전환한다.
- 친구 랭킹은 본인 + 친구 목록으로 조회 범위를 한정한다.

## 11. 관리자 규칙 (담당: 팀원 4)

- 관리자가 등록한 퀘스트는 `QUESTS.created_by = ADMIN`으로 구분하되, 일반 퀘스트와 동일하게 배정 풀에 포함된다.
- `is_active = false`인 퀘스트는 배정 대상에서 제외된다(즉시 삭제 대신 비활성화를 우선 사용).

## 12. 예외 케이스 정리

| 상황 | 처리 방침 |
|---|---|
| 위치 권한 거부 | 권한 요청 화면 재표시, LOCATION 퀘스트 진행 불가 안내 |
| GPS 비활성화 | 위치 설정 안내 화면 표시 |
| 인증 반경 밖 | 현재 거리·필요 이동 거리 안내, 완료 처리 거부 |
| 이미 완료한 퀘스트 재요청 | 기존 결과 반환, 재지급 없음(§4) |
| 만료된 배정 건 완료 시도 | `QUEST_EXPIRED` 오류 반환 |
| 존재하지 않는 사용자에게 친구 요청 | `RESOURCE_NOT_FOUND` 오류 반환 |
| 이미 친구인 사용자에게 재요청 | `DUPLICATE_FRIEND_REQUEST` 오류 반환 |
